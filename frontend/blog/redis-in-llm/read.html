Redis 在 LLM 应用中的实战：限流、缓存与进度追踪

面试中只要提到"大模型网关"或"高并发后端"，Redis 是绕不开的话题。这篇文章结合我实习中真实使用 Redis 的三个场景——分布式限流、负载均衡状态管理、异步任务进度追踪——从应用场景到底层原理讲透。

一、为什么 LLM 网关必须用 Redis 而不是单机内存？

一句话：网关是多节点分布式部署的。

我们的 LiteLLM 网关通过 Docker Compose 部署，支持水平扩容。假设你起了 3 个网关实例，如果限流计数器只存在 Node A 的内存里，Node B 的请求根本感知不到，限流就形同虚设。

Redis 作为独立的外部存储，天然适合做分布式状态共享：

# docker-compose.yml
redis:
  image: redis:7-alpine
  container_name: litellm-redis
  ports:
    - "6379:6379"
  volumes:
    - redis_data:/data

二、场景一：分布式全局限流（Rate Limiting）

LLM API 调用有两种限流维度：

  • RPM（Requests Per Minute）：每分钟请求次数
  • TPM（Tokens Per Minute）：每分钟 Token 消耗量

比如控制某个租户 TPM 不超过 10 万，必须用 Redis 来保证多节点数据一致性。

2.1 滑动窗口算法（Sliding Window）

最常用的是滑动窗口。Redis 实现非常自然——利用 Sorted Set（ZSET）：

# Redis 滑动窗口伪代码
import time
import redis

r = redis.Redis()

def check_rate_limit(user_id: str, max_rpm: int, max_tpm: int,
                     current_tokens: int) -> bool:
    now = time.time()
    window_start = now - 60  # 1 分钟窗口

    key_rpm = f"ratelimit:rpm:{user_id}"
    key_tpm = f"ratelimit:tpm:{user_id}"

    # 1. 删除窗口外的过期记录
    r.zremrangebyscore(key_rpm, 0, window_start)
    r.zremrangebyscore(key_tpm, 0, window_start)

    # 2. 统计窗口内的当前值
    current_rpm = r.zcard(key_rpm)           # RPM 看请求次数
    current_tpm = r.zcount(key_tpm, 0, now)  # TPM 看 Token 量

    # 3. 判断是否超额
    if current_rpm >= max_rpm or current_tpm + current_tokens > max_tpm:
        return False  # 触发限流，返回 HTTP 429

    # 4. 记录本次请求
    r.zadd(key_rpm, {str(now): now})
    r.zadd(key_tpm, {f"{now}:{current_tokens}": current_tokens})
    r.expire(key_rpm, 120)   # 设置过期避免内存泄漏
    r.expire(key_tpm, 120)

    return True

2.2 令牌桶算法（Token Bucket）

另一种常见算法。核心思想：

  • 桶以固定速率产生 Token（比如每秒 1667 Token）
  • 每次请求消耗对应 Token 数
  • 桶空了就触发限流

Redis 实现可以用 Lua 脚本保证原子性：

-- Redis Lua 脚本：令牌桶
local key = KEYS[1]
local capacity = tonumber(ARGV[1])    -- 桶容量
local rate = tonumber(ARGV[2])        -- 每秒产生 Token 数
local requested = tonumber(ARGV[3])   -- 本次请求需要的 Token 数
local now = tonumber(ARGV[4])

local bucket = redis.call('HMGET', key, 'tokens', 'last_time')
local tokens = tonumber(bucket[1]) or capacity
local last_time = tonumber(bucket[2]) or now

-- 计算这段时间新产生的 Token
local delta = math.max(0, now - last_time)
local new_tokens = math.min(capacity, tokens + delta * rate)

if new_tokens >= requested then
    redis.call('HMSET', key, 'tokens', new_tokens - requested, 'last_time', now)
    redis.call('EXPIRE', key, 120)
    return 1  -- 放行
else
    return 0  -- 限流
end

为什么用 Lua？因为 Redis 的 Lua 脚本是原子执行的，不会有竞态条件。如果用客户端多次调用 GET + SET，在高并发下会出现"超卖"。

三、场景二：负载均衡的 in-flight 请求追踪

LiteLLM 的 Least Busy 路由策略需要在 Redis 中维护每个节点的当前活跃请求数：

# 请求分发前
r.hincrby("deployment:in_flight", deployment_id, 1)

# 请求完成后（无论成功失败）
r.hincrby("deployment:in_flight", deployment_id, -1)

# 路由时选择 in_flight 最小的节点
inflight = r.hgetall("deployment:in_flight")
best_deployment = min(inflight, key=lambda k: int(inflight[k]))

另一个关键用途是节点冷却标记。当一个节点返回 429 或 500 时，在 Redis 中标记冷却期：

# 节点故障，标记 60 秒冷却
r.setex(f"cooldown:{deployment_id}", 60, "1")

# 路由时跳过冷却中的节点
if r.exists(f"cooldown:{deployment_id}"):
    continue  # 跳过这个节点

四、场景三：异步任务进度追踪

在 MathTasks 项目中，AI 难度验证是异步任务——提交后 Worker 慢慢跑，前端需要实时看到进度。我们用 Redis 做进度缓存：

# Worker 更新进度到 Redis
def update_progress(task_id: str, progress: int, status: str):
    r.hset(f"task:{task_id}", mapping={
        "progress": progress,
        "status": status,       # "running" | "completed" | "failed"
        "updated_at": time.time()
    })
    r.expire(f"task:{task_id}", 3600)  # 1 小时后过期

# 前端通过 SSE 端点获取进度（后端从 Redis 读）
def get_progress(task_id: str):
    data = r.hgetall(f"task:{task_id}")
    return {
        "progress": int(data.get("progress", 0)),
        "status": data.get("status", "unknown")
    }

这个设计的演进过程也值得一提：最初版本是纯内存轮询 → 后来引入 Redis → 最终升级为 SSE 实时推送（Redis 作为 SSE 断线重连时的状态恢复源）。

五、面试必考：缓存三连

面试官问你 Redis，几乎一定会追问缓存雪崩、缓存击穿、缓存穿透。结合 LLM 网关场景来回答：

5.1 缓存穿透（Cache Penetration）

现象：查一个不存在的 API Key，缓存里没有，每次都穿透到 PostgreSQL 查询。
解法：布隆过滤器（Bloom Filter）预先过滤不存在的 Key，或者把"不存在"也缓存一个空值（设短 TTL）。

5.2 缓存击穿（Cache Breakdown）

现象：热点数据（比如某个高频租户的限流计数器）的 Key 刚好过期，瞬间大量请求同时打到数据库。
解法：互斥锁（Mutex Lock）——第一个请求去查 DB 并重建缓存，其他请求等待；或者"永不过期" + 异步刷新。

5.3 缓存雪崩（Cache Avalanche）

现象：大量 Key 在同一时间集体过期（或 Redis 宕机），所有请求直接打到数据库。
解法：Key 的过期时间加随机偏移（TTL = 3600 + random(0, 600)）；Redis 集群/哨兵模式保证高可用。

总结

Redis 在 LLM 应用中扮演"高性能状态共享层"的角色，核心用途：

  • 分布式限流：滑动窗口 / 令牌桶，Lua 原子操作
  • 负载均衡状态：in-flight 计数 + 节点冷却标记
  • 进度追踪：异步任务的状态缓存，SSE 断线重连的数据源

面试官问到 Redis，如果能把这三种场景和三种缓存问题都讲清楚，基本就通关了。
