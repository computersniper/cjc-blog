大模型网关的可观测性：Langfuse 集成与 Callback 机制解析

面试官问你"Langfuse 是什么"以及"它的源码是怎么工作的"，本质上是在考查你是否懂大模型系统的可观测性（Observability），以及你对网关性能（非阻塞）的理解。这篇文章分三个层次：业务价值 → 源码集成机制 → 性能与高可用保障。

第一层：为什么网关必须接入可观测性？

一个只做请求转发的网关是"黑盒"。Langfuse 作为开源可观测性平台，解决了三大痛点：全链路追踪（Tracing，记录 Prompt/响应/TTFT）、精准计费（自动解析 Token 消耗并换算成本）、降级与错误分析（Trace 树清晰展示 Fallback 链路）。

第二层：Callback 钩子架构

LiteLLM 集成 Langfuse 靠的是观察者模式（Observer Pattern）。在 config.yaml 中声明 success_callback: ["langfuse"] 和 failure_callback: ["langfuse"]。每次 completion() 结束后，遍历所有 Callback 钩子。litellm/integrations/langfuse.py 中的 LangfuseLogger 类接收 kwargs（原始 messages）和 response（usage 字段），创建 Trace 和 Generation 数据模型，通过 langfuse-python SDK 发送。

第三层：性能保障——旁路监控不阻塞主链路

三个层面保证：1) 主请求剥离——Callback 挂载到 asyncio.create_task，主函数立刻 return；2) 批量队列发送——SDK 维护后台线程和内存队列，攒批后统一 POST；3) 容灾断开——Langfuse 不可用时自动丢弃监控数据，绝不抛异常影响用户请求。

面试话术："Langfuse 上报完全异步非阻塞——asyncio.create_task 剥离 + SDK 内存队列批量发送 + 故障自动丢弃，不增加用户 TTFT。"

Trace 与 Generation 层级

Trace 代表一次完整会话，Generation 是 Trace 下的单次 LLM 调用。如果触发 Fallback（GPT-4o 失败 → Claude），同一个 Trace 下会有两个 Generation，方便定位性能瓶颈。
