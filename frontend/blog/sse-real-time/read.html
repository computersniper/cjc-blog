SSE 实时推送实战：从心跳保活到断线重连

SSE Real-time Push: From Heartbeat Keep-alive to Reconnection Recovery

在 MathTasks 项目中，AI 处理一道数学题需要数分钟——难度评估、向量查重、质量检测三个异步队列并行跑。用户不能盯着空白页面干等。我们选择 SSE（Server-Sent Events） 而非 WebSocket，这篇文章从架构设计、核心源码、到踩坑经验全部分享。

一、为什么选 SSE 而不是 WebSocket？

两者都能做服务端推送，但场景不同：

维度 SSE WebSocket
通信方向 单向（服务端 → 客户端） 双向
协议 HTTP（标准 HTTP 长连接） WS（独立协议，需升级握手）
断线重连 浏览器原生支持（EventSource API） 需手动实现
Nginx 代理 开箱即用（普通 HTTP 代理即可） 需额外配置 Upgrade 头

MathTasks 的需求是"服务端推送进度给前端，前端不主动发消息"。SSE 完美匹配——更轻量、更易部署、浏览器自带重连。

二、SSE 连接管理器：全局单例设计

核心代码在 services/sse_manager.py，设计为一个全局单例：

class SSEConnectionManager:
    """SSE 连接管理器（全局单例）"""

    def __init__(self) -> None:
        self.clients: Dict[str, asyncio.Queue] = {}        # client_id → 消息队列
        self.user_clients: Dict[int, Set[str]] = defaultdict(set)  # user_id → client_id 集合
        self._last_activity: Dict[str, float] = {}          # 最后活跃时间戳
        self._cleanup_task: asyncio.Task | None = None
        self._is_shutting_down = False

关键设计决策：

  • 每个 client_id 一个独立 asyncio.Queue：同一用户多标签页互不干扰
  • user_clients 映射：支持按用户维度广播消息（比如"你的题目处理完了"）
  • 队列积压上限 200：防止慢消费客户端耗尽服务端内存

三、客户端注册与消息推送

3.1 注册流程

async def register_client(self, client_id: str, user_id: int) -> asyncio.Queue:
    queue: asyncio.Queue = asyncio.Queue(maxsize=200)
    self.clients[client_id] = queue
    self.user_clients[user_id].add(client_id)
    self._last_activity[client_id] = time.time()

    # 确保清理协程已启动
    if self._cleanup_task is None or self._cleanup_task.done():
        self._cleanup_task = asyncio.create_task(self._cleanup_stale_connections())

    return queue

3.2 推送到指定用户的所有客户端

def push_to_user(self, user_id: int, message: SSEMessage) -> None:
    client_ids = self.user_clients.get(user_id, set())
    if not client_ids:
        return  # 无活跃连接，消息丢弃

    data = message.model_dump()
    for cid in list(client_ids):
        self._enqueue(cid, data)

3.3 入队保护

def _enqueue(self, client_id: str, data: dict) -> None:
    queue = self.clients.get(client_id)
    if not queue:
        return
    try:
        queue.put_nowait(data)
        self._last_activity[client_id] = time.time()
    except asyncio.QueueFull:
        logger.warning("客户端 %s 队列已满，丢弃消息", client_id)

put_nowait 是非阻塞的——如果队列满了直接丢弃并打 Warning，不会卡住生产者线程。

四、心跳保活机制

HTTP 长连接可能被中间代理（Nginx、LB）静默断开。心跳是保活的关键：

# SSE 路由中的心跳逻辑
_HEARTBEAT_INTERVAL = 15  # 每 15 秒发一次心跳

async def event_generator():
    last_heartbeat = time.time()

    while True:
        try:
            # 等待消息，1 秒超时用于检查心跳
            message = await asyncio.wait_for(queue.get(), timeout=1.0)
            yield "data: " + json.dumps(message) + "\n\n"
        except asyncio.TimeoutError:
            pass  # 超时不是错误，只是没消息

        # 定期发送心跳
        now = time.time()
        if now - last_heartbeat >= _HEARTBEAT_INTERVAL:
            yield "data: " + json.dumps({
                "type": "heartbeat",
                "payload": {"server_time": int(now * 1000)},
                "timestamp": int(now * 1000)
            }) + "\n\n"
            sse_manager.touch(client_id)  # 更新活跃时间
            last_heartbeat = now

心跳做了两件事：

  1. 保持 TCP 连接不被代理断开
  2. 让客户端感知服务端存活——前端可以据此判断连接状态

五、僵尸连接清理

客户端可能异常断开（关浏览器、网络切换），服务端如果不清这些"僵尸连接"，内存会慢慢泄漏：

async def _cleanup_stale_connections(self) -> None:
    """每 30 秒检查一次，120 秒无活动的连接视为僵尸"""
    stale_timeout = 120
    check_interval = 30

    while True:
        await asyncio.sleep(check_interval)
        now = time.time()
        stale = [
            cid for cid, ts in self._last_activity.items()
            if now - ts > stale_timeout
        ]
        for cid in stale:
            logger.info("清理僵尸连接 client_id=%s", cid)
            await self.unregister_client(cid)

设计要点：

  • 120 秒无活动才清理——留足够容错空间（心跳 15 秒，即使漏几次也不会被误杀）
  • 清理间隔 30 秒——不频繁扫描，避免 CPU 消耗
  • 清理任务作为后台协程自动启动——无需外部触发

六、优雅停机

服务重启时，应该通知所有已连接客户端：

# 设置停机标志
sse_manager.set_shutdown(True)

# SSE 路由检查停机状态
async def event_generator():
    ...
    while True:
        ...
        if sse_manager.is_shutting_down():
            yield "data: " + json.dumps({
                "type": "server_shutdown",
                "payload": {"reason": "shutdown"}
            }) + "\n\n"
            break  # 退出事件循环

# 新连接在停机期间被拒绝
@router.get("/stream")
async def sse_stream(request: Request):
    if sse_manager.is_shutting_down():
        raise HTTPException(status_code=503, detail="服务正在关闭")

七、断线重连：Redis 作为状态恢复源

SSE 连接断了之后，前端利用 EventSource 的自动重连特性重新建立连接。但重连后如何恢复之前的进度？

解决方案：Worker 处理进度时不只发 SSE，同时写入 Redis。前端重连后，先请求当前进度快照（从 Redis 读），然后再订阅 SSE：

# 前端重连流程
1. EventSource 检测到连接断开
2. 浏览器自动重连（EventSource 原生行为）
3. 收到 "connected" 事件后，请求 GET /api/progress/{task_id}
4. 后端从 Redis 读取当前进度，一次性返回快照
5. 前端渲染快照，同时继续监听 SSE 增量更新

这个"Redis 做状态兜底 + SSE 做实时推送"的双通道设计，是我们在 MathTasks 中迭代出来的成熟方案。

八、Nginx 兼容性配置

SSE 经过 Nginx 反向代理时，需要关闭缓冲：

# Nginx 配置 SSE 端点
location /api/sse/stream {
    proxy_pass http://backend;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_buffering off;           # ← 关键：关闭代理缓冲
    proxy_cache off;
    proxy_read_timeout 86400s;     # 长连接超时设为 24 小时
}

服务端也要设置响应头：

return StreamingResponse(
    event_generator(),
    media_type="text/event-stream",
    headers={
        "Cache-Control": "no-cache",
        "Connection": "keep-alive",
        "X-Accel-Buffering": "no",   # 显式禁用 Nginx 缓冲
    },
)

九、架构演进历程

这不是一开始就设计出来的。实际经历了三个版本的迭代：

  1. V1：前端轮询——每 2 秒 GET 一次进度接口。简单但浪费带宽，进度更新不及时
  2. V2：Redis + 轮询——Worker 写 Redis，前端轮询读 Redis。比 V1 好，但仍有轮询延迟
  3. V3：SSE + Redis 兜底——SSE 实时推送，Redis 作为断线重连时的状态恢复源。当前生产方案

每次演进都是被"用户体感延迟"驱动的。V3 后，题目处理进度从"2 秒滞后"变成了"实时"。

总结

一个生产级的 SSE 实现，至少需要考虑这 5 点：

  • 连接管理：全局单例 + 按用户维度路由 + 队列积压保护
  • 心跳保活：15 秒间隔 + touch 活跃时间
  • 僵尸清理：后台协程 + 120 秒超时
  • 优雅停机：通知客户端 + 拒绝新连接
  • 断线重连：Redis 状态兜底 + EventSource 自动重连

这 5 点齐了，你的 SSE 方案就敢说"生产可用"。

In the MathTasks project, AI processing of a single math problem takes several minutes — difficulty assessment, vector-based deduplication, and quality inspection run in three parallel async queues. Users can't just stare at a blank page waiting. We chose SSE (Server-Sent Events) over WebSocket. This article shares everything from architecture design and core source code to hard-won lessons learned.

1. Why SSE Over WebSocket?

Both support server-side push, but they suit different scenarios:

Dimension SSE WebSocket
Communication Direction Unidirectional (Server → Client) Bidirectional
Protocol HTTP (standard HTTP long connection) WS (separate protocol, requires upgrade handshake)
Reconnection Native browser support (EventSource API) Manual implementation required
Nginx Proxy Works out of the box (standard HTTP proxy) Requires extra Upgrade header config

MathTasks' requirement is "server pushes progress to the frontend, the frontend doesn't actively send messages." SSE is a perfect match — lighter weight, easier to deploy, with browser-native reconnection.

2. SSE Connection Manager: Global Singleton Design

The core code lives in services/sse_manager.py, designed as a global singleton:

class SSEConnectionManager:
    """SSE 连接管理器（全局单例）"""

    def __init__(self) -> None:
        self.clients: Dict[str, asyncio.Queue] = {}        # client_id → 消息队列
        self.user_clients: Dict[int, Set[str]] = defaultdict(set)  # user_id → client_id 集合
        self._last_activity: Dict[str, float] = {}          # 最后活跃时间戳
        self._cleanup_task: asyncio.Task | None = None
        self._is_shutting_down = False

Key design decisions:

  • One independent asyncio.Queue per client_id: Multiple tabs for the same user don't interfere with each other
  • user_clients mapping: Supports broadcasting messages by user dimension (e.g., "your problem has been processed")
  • Queue backlog limit of 200: Prevents slow-consuming clients from exhausting server memory

3. Client Registration and Message Push

3.1 Registration Flow

def push_to_user(self, user_id: int, message: SSEMessage) -> None:

3.3 Enqueue Protection

def _enqueue(self, client_id: str, data: dict) -> None:
    queue = self.clients.get(client_id)
    if not queue:
        return
    try:
        queue.put_nowait(data)
        self._last_activity[client_id] = time.time()
    except asyncio.QueueFull:
        logger.warning("客户端 %s 队列已满，丢弃消息", client_id)

put_nowait is non-blocking — if the queue is full, it simply drops the message and logs a Warning, without blocking the producer thread.

4. Heartbeat Keep-Alive Mechanism

HTTP long connections can be silently dropped by intermediate proxies (Nginx, load balancers). Heartbeats are the key to staying alive:

# SSE 路由中的心跳逻辑
_HEARTBEAT_INTERVAL = 15  # 每 15 秒发一次心跳

async def event_generator():
    last_heartbeat = time.time()

    while True:
        try:
            # 等待消息，1 秒超时用于检查心跳
            message = await asyncio.wait_for(queue.get(), timeout=1.0)
            yield "data: " + json.dumps(message) + "\n\n"
        except asyncio.TimeoutError:
            pass  # 超时不是错误，只是没消息

        # 定期发送心跳
        now = time.time()
        if now - last_heartbeat >= _HEARTBEAT_INTERVAL:
            yield "data: " + json.dumps({
                "type": "heartbeat",
                "payload": {"server_time": int(now * 1000)},
                "timestamp": int(now * 1000)
            }) + "\n\n"
            sse_manager.touch(client_id)  # 更新活跃时间
            last_heartbeat = now

Heartbeats accomplish two things:

  1. Keep the TCP connection from being dropped by proxies
  2. Let the client know the server is alive — the frontend can use this to determine connection health

5. Zombie Connection Cleanup

Clients may disconnect abnormally (closing the browser, network switching). If the server doesn't clean up these "zombie connections," memory will slowly leak:

async def _cleanup_stale_connections(self) -> None:
    """每 30 秒检查一次，120 秒无活动的连接视为僵尸"""
    stale_timeout = 120
    check_interval = 30

    while True:
        await asyncio.sleep(check_interval)
        now = time.time()
        stale = [
            cid for cid, ts in self._last_activity.items()
            if now - ts > stale_timeout
        ]
        for cid in stale:
            logger.info("清理僵尸连接 client_id=%s", cid)
            await self.unregister_client(cid)

Design considerations:

  • Clean up only after 120 seconds of inactivity — leaving enough fault tolerance (heartbeat is every 15 seconds, so missing a few won't trigger a false kill)
  • Cleanup interval of 30 seconds — infrequent scanning to avoid CPU overhead
  • Cleanup task auto-starts as a background coroutine — no external trigger needed

6. Graceful Shutdown

When the service restarts, all connected clients should be notified:

# 设置停机标志
sse_manager.set_shutdown(True)

# SSE 路由检查停机状态
async def event_generator():
    ...
    while True:
        ...
        if sse_manager.is_shutting_down():
            yield "data: " + json.dumps({
                "type": "server_shutdown",
                "payload": {"reason": "shutdown"}
            }) + "\n\n"
            break  # 退出事件循环

# 新连接在停机期间被拒绝
@router.get("/stream")
async def sse_stream(request: Request):
    if sse_manager.is_shutting_down():
        raise HTTPException(status_code=503, detail="服务正在关闭")

7. Reconnection: Redis as the State Recovery Source

After an SSE connection drops, the frontend leverages EventSource's auto-reconnect feature to re-establish the connection. But how do you recover the previous progress after reconnecting?

The solution: When the Worker processes progress, it doesn't just send SSE — it also writes to Redis simultaneously. After the frontend reconnects, it first requests a current progress snapshot (from Redis), then subscribes to SSE:

# 前端重连流程
1. EventSource 检测到连接断开
2. 浏览器自动重连（EventSource 原生行为）
3. 收到 "connected" 事件后，请求 GET /api/progress/{task_id}
4. 后端从 Redis 读取当前进度，一次性返回快照
5. 前端渲染快照，同时继续监听 SSE 增量更新

This dual-channel design of "Redis as the state safety net + SSE for real-time push" is a proven solution we iterated on in MathTasks.

9. Architecture Evolution

This wasn't designed upfront. It actually went through three iterations:

  1. V1: Frontend Polling — GET the progress endpoint every 2 seconds. Simple but wasteful on bandwidth, with delayed progress updates
  2. V2: Redis + Polling — Worker writes to Redis, frontend polls Redis. Better than V1, but still has polling latency
  3. V3: SSE + Redis Safety Net — SSE for real-time push, Redis as the state recovery source for reconnection. Current production solution

Each evolution was driven by "perceived user latency." After V3, problem processing progress went from "2-second lag" to "real-time."

Summary

A production-grade SSE implementation needs to address at least these five aspects:

  • Connection Management: Global singleton + user-dimension routing + queue backlog protection
  • Heartbeat Keep-Alive: 15-second interval + touch activity timestamp
  • Zombie Cleanup: Background coroutine + 120-second timeout
  • Graceful Shutdown: Notify clients + reject new connections
  • Reconnection Recovery: Redis state safety net + EventSource auto-reconnect

Get these five right, and your SSE solution can confidently be called "production-ready."
